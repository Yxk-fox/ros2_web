摘　要

本文档面向技术开发团队，系统阐述 Mock Truck 管理工具的架构设计、目录约定、API 清单、install 多版本管理机制、数据库适配、安全机制与二次开发规范。后端采用 core、database、services、routers 四层解耦架构，入口文件 app.py 仅承担装配职责；v4.0 引入数据导出模块（hdmap 提取与 bag 录制）；v5.0 实现 install 安装目录多版本上传、切换与删除，所有 ROS2 / Docker / 脚本操作均在所选版本目录下执行。前端为独立静态文件，通过 REST API 与 WebSocket 与后端交互。本文档旨在为维护者提供足够的设计上下文，使其能够安全地进行功能扩展与缺陷修复。

一、系统架构总览

系统采用前后端分离架构。后端基于 FastAPI 提供 REST API 与 WebSocket，封装 Docker、ROS2 与系统资源的调用；前端为纯静态站点，通过 apiGet / apiPost 封装访问后端。鉴权使用 JWT，数据库支持 JSON 文件与 Supabase 两种适配器，可按配置切换。v5.0 起，install 安装目录支持多版本并行存储与按用户切换，版本选择状态持久化于用户表 current_version 字段，核心业务（脚本生成、仿真控制、话题节点）通过统一的路径解析函数获取当前生效的 install 目录。

二、后端目录结构与职责

后端代码位于 backend/ 目录，遵循四层分离原则。

表 2-1　后端目录职责
路径职责关键文件
app.py入口，创建应用、注册中间件、挂载路由与静态文件app.py
core/配置、常量、安全、工具、缓存、中间件、工作空间config.py、constants.py、security.py、utils.py、workspace.py
database/数据库适配器，支持 JSON 与 Supabasejson_db.py、supabase_db.py、__init__.py
services/业务服务，封装 Docker、脚本生成、监控等docker_manager.py、script_generator.py、system_monitor.py、traffic_light.py
routers/统一 API 路由（可按领域拆分）api.py
deps.py依赖注入：当前用户、权限校验deps.py
models.pyPydantic 数据模型models.py
logger.py统一日志配置logger.py

2.1 core 层要点

  • config.py：运行时配置加载与热保存，配置文件为 config.json。
  • constants.py：集中常量（端口、路径、权限点、可视化配置、缓存与 WebSocket 客户端容器等）。
  • security.py：密码哈希、JWT 签发与校验、命令清洗、速率限制器。
  • workspace.py：用户工作空间路径校验与创建，支撑多用户资源隔离。

2.2 services 层要点

  • DockerManager：封装 docker ps / inspect / kill / update / exec 等，统一带 sudo 前缀（DOCKER_PREFIX）。
  • SystemMonitor：采集 CPU、内存、GPU（nvidia-smi）与进程列表。
  • ROS2ScriptGenerator：依据 launch 文件生成启动脚本，脚本内 install 路径随当前版本目录动态生成。
  • TrafficLightSender / TimerTrafficLightSender：红绿灯模拟的云端联动与计时模式。
  • InstallVersionManager（v5.0）：install 版本目录的识别、归档、上传解压、切换与删除，含备份目录自愈。
  • DataExporter（v4.0）：hdmap 地图提取、ros2 bag 全话题录制与打包下载。

五、WebSocket 通信

系统通过 WebSocket 实现终端、实时日志与消息推送。连接客户端集中维护于 core/constants.ws_clients。鉴权时 Token 通过查询参数或首条消息传递，连接建立后绑定到用户上下文。

  • 终端：/ws/terminal/{container}，前端 terminal.js 负责收发。
  • 实时日志：流式推送 docker logs -f 输出。
  • 广播日志：broadcast_log 工具函数向全部在线客户端推送系统消息。

六、数据库适配层

database/ 提供统一接口 db，底层可切换 JSON 文件或 Supabase。

适配器适用场景存储
json_db.py单机、轻量、无外部依赖data/data.json、data/audit_logs.json

6.1 用户表新增字段（v5.0）

为持久化每用户的 install 版本选择，users 表新增 current_version 字段（TEXT，默认空串，空表示使用旧版 install 目录）：

ALTER TABLE public.users ADD COLUMN IF NOT EXISTS current_version TEXT DEFAULT '';

两个适配器均已同步支持该字段：JSON 适配器在启动时自动为存量用户补齐字段；Supabase 适配器在字段缺失时（PostgREST 返回 PGRST204）会打印上述修复 SQL 并自动降级为“会话级记忆”（切换当次可用，重启丢失），字段补齐后无需重启服务即自动恢复持久化。

七、install 多版本管理机制（v5.0）

7.1 目录结构

每个用户工作空间下的版本目录按“压缩包顶层目录名”归档：

<工作空间>/                          如 ~/robotruck_ros2/<用户>/
├── install/                          旧版安装目录（兼容保留，可回退）
├── <版本A>/
│   └── install/
│       ├── setup.bash
│       └── ...
├── <版本B>/
│   └── install/
├── <版本B>.bak.<时间戳>/            重传同名版本时的自动备份（保留最近 2 份）
└── <版本>.deleted.<时间戳>/          删除版本时的软删除目录（不物理删除）

版本识别规则：工作空间下任何包含 install/setup.bash 的一级子目录视为有效版本；带 .deleted / .bak / .replaced 后缀的目录视为备份，不计入版本列表。

7.2 切换流程

  1. 前端提交目标版本名，后端校验该版本目录有效。
  2. 更新用户表 current_version 字段（持久化）。
  3. 返回新版本信息，前端约 1 秒后整页刷新，侧边栏徽标与所有面板重新加载。
  4. 此后脚本生成、仿真控制、话题节点等接口统一按 <工作空间>/<版本>/install/ 解析路径。
警告：已生成的启动脚本内路径是固化的，切换版本不会自动改写历史脚本；删除当前生效版本时，系统自动清理 Docker 生成产物并切换到剩余最新版本，无剩余版本则回退旧版 install。

7.3 上传归档流程

  1. 前端分片上传压缩包（.zip / .tar.gz / .tgz / .tar.bz2 / .tar，上限 5 GB）至服务端临时目录。
  2. 解压后按顶层目录名归档为版本目录；同名版本先改名备份（.replaced 后缀，保留最近 2 份）。
  3. 校验 install/setup.bash 存在后自动切换到新版本并清理临时文件。
  4. 审计日志记录上传人、版本名与文件大小。

八、安全机制

  • JWT 鉴权：HS256，默认 1 天有效期，记住我可延至 7/15/30 天。
  • 密码哈希：bcrypt，轮数可配（默认 12）。
  • 速率限制：基于 slowapi，登录注册默认 5 次 / 分钟。
  • 命令清洗：sanitize_command 对容器内执行命令做白名单过滤（可配）。
  • 权限校验：require_permission / require_admin 依赖注入；数据导出受 data-export 权限点控制。
  • 审计日志：登录、容器操作、用户管理、版本切换与删除、数据导出等写入审计库，可查询与清理。
  • 资源隔离：普通用户仅可见与操作自有资源，_check_container_access 校验归属；版本管理中普通用户不可指定 target_user，仅管理员可代他人操作。
警告：修改安全相关逻辑（JWT 密钥、命令白名单、权限点）须充分回归测试，避免引入越权或命令注入风险。

九、二次开发规范

9.1 新增 API

  1. 在 routers/api.py 中新增路由函数，使用 @router.get/post 装饰器。
  2. 按需注入 get_current_user / require_permission / require_admin。
  3. 业务逻辑放入 services/ 对应类，保持路由层轻量。
  4. 涉及配置的项写入 config.json 与 core/constants.py。
  5. 关键操作写入审计日志（db.add_audit_log）。

9.2 新增前端面板

  1. 在 index.html 增加 <div class="panel" id="panel-xxx">。
  2. 在导航栏增加对应 nav-item，data-panel 指向新面板。
  3. 逻辑写入 sj_script.js，复用 apiGet/apiPost 与 showToast。
  4. 需要权限控制的按钮加 admin-only 类或运行时判断 hasPermission。

9.3 编码约定

  • Python 遵循 PEP 8，类型注解齐全；前端兼容老浏览器，使用 ES5 兼容写法（var、函数表达式）。
  • 新增常量集中到 constants.py，避免散落硬编码。
  • 外部命令统一经 DockerManager.run_cmd，带超时与错误处理。
  • 涉及时间的展示一律以后端权威时间为准，前端不得自维护本地时钟态。

十、部署与运维

部署脚本 deploy.py 支持 --skip-system / --skip-deps / --only-deps 参数，可批量检查并安装依赖、生成 systemd 服务。依赖清单见 redame/requirements.txt。脚本已适配所有服务器，换机器、换用户名均无需修改任何内容。

10.1 跨服务器自动适配

  • 用户名自动获取：按 SUDO_USER（sudo 执行时的真实用户）→ LOGNAME / USER / USERNAME 环境变量 → getpass.getuser() 兜底的顺序解析。不使用 os.getlogin()，因其依赖控制终端，在 systemd / cron / 无 tty 的 ssh 环境下会抛 OSError。
  • 路径自动推导：项目目录基于脚本所在位置推导，用户家目录由用户名解析，Python 解释器经 shutil.which("python3") 定位，无任何硬编码。
  • docker 组自动配置：部署时自动检测执行用户是否已在 docker 组（id -nG 校验，/etc/group 兜底），未入组则自动执行 usermod -aG docker <用户>；已入组自动跳过。加入后需重新登录生效。

10.2 sudo 权限提示

未加 sudo 直接运行 python3 deploy.py 时，脚本不会静默失败，而是给出明确指引：提示使用 sudo python3 deploy.py 重新执行（sudo 将提示输入当前用户密码），并支持输入 y 由脚本自动以 sudo 重新拉起自身继续部署。--only-deps 模式仅安装 Python 依赖，可免 sudo 运行。

注意：systemd 服务以实际执行用户（sudo 前的真实用户）身份运行，日志与数据目录归属自动正确。直接以 root 身份执行（无 SUDO_USER）时，脚本会跳过 docker 组配置并给出手动处理指引。
  • 服务默认监听 0.0.0.0:8875，CORS 通过 config.json 配置。
  • 日志文件 audit.log 与 data/audit_logs.json 按需轮转。
  • 升级时优先在测试环境验证，确认 API 兼容后再推生产。
