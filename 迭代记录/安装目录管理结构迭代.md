| 2 | 普通用户可在**首页**下拉切换不同版本进行测试 | ✅ 首页「安装目录管理」卡片提供版本下拉 + 切换/删除 |

### 1.2 目录结构（版本化后）

```
<用户工作空间>/
├── Docker/                    # bags/logs/scripts/bk 等运行产物（与版本无关，用户级）
├── install/                   # 【旧版路径】存量兼容，current_version 为空时回退到此
├── test_install20260904_x86_ros2_5.0/      # 版本目录（= 版本号 = 压缩包顶层目录名）
│   └── install/
│       ├── setup.bash
│       └── simulation_launches/...
├── test_install20260922_x86_ros2_3.0/
│   └── install/...
└── <版本名>.replaced.<时间戳>/             # 同名重传时旧版本自动备份（保留最近 2 个）
```

要点：

- **版本目录名即版本号**，同一工作空间内可并存任意多个版本。
- 版本目录之间互不覆盖；重传同名版本时，旧目录整体改名备份（`<名>.replaced.<YYYYMMDD_HHMMSS>`），最多保留 2 份。
- 删除中的备份目录（`.deleted.<时间戳>` / `.bak.<时间戳>` / `.replaced.<时间戳>`）不会出现在版本列表中。

## 2. 总体设计

### 2.1 版本模型

- 每个**用户记录**新增一个字符串字段 `current_version`：
  - 非空 = 当前选定的版本目录名；
  - 空串 = 未选版本，回退旧版 `<工作空间>/install/`。
- 版本选择是**用户级状态**：管理员与普通用户各自独立；管理员还可通过 `target_user` 操作/查看指定用户空间的版本。
- 版本目录物理上存放在**各用户自己的工作空间**内，遵循既有的用户隔离架构，用户之间互不可见。

### 2.2 install 路径解析优先级

统一由 `resolve_versioned_install()` 实现（`backend/core/workspace.py:85`）：

1. `current_version` 合法且 `<工作空间>/<版本>/install` 存在 → 使用版本目录；
2. 否则旧版 `<工作空间>/install` 存在 → 回退旧版路径（并把 `current_version` 视为空，保证存量环境零感知）；
3. `current_version` 非空但版本目录缺失、且无旧版 → 仍指向版本路径（表示"已选择、等待上传"状态）；
4. 兜底 → 旧版路径。

返回结构：
```python
{"current_version": str | None, "install_dir": str,
 "version_dir": str, "is_versioned": bool}
```

### 2.3 全局生效机制（关键）

全系统只有一个入口解析工作路径：`get_user_workspace_paths()`（`backend/core/workspace.py:172`）。
所有路由（脚本生成、仿真控制、话题/节点/服务/Action、工单、高级/拓展功能、系统监控、REST API 管理等）都通过它取得：

- `host_install` / `launch_dir` / `config_dir`：在 v5.0 中全部基于 `resolved["install_dir"]` 拼接（`workspace.py:209-222`、`workspace.py:237-257`）；
- 并向调用方透传 `current_version` / `version_dir` / `is_versioned` / `versions`。

因此版本切换在后端是"一处解析、处处生效"，菜单代码无需逐个修改。

- **宿主机 ROS2 命令**：`run_ros2_cmd()` 会 source 管理员当前生效版本的 `setup.bash`（`backend/core/utils.py:187-201`，经 `get_admin_install_dir()` 解析，`workspace.py:120`）。
- **容器内命令**：统一 source 容器固定挂载路径 `/home/boonray/install/setup.bash`（配置项 `container_install`）；版本切换后通过重新启动仿真容器，使宿主机当前版本目录挂载到该固定路径，从而容器内也运行在所选版本下。
- **注意**：切换版本前已生成的启动脚本内路径是固化的，切换后需要重新生成脚本（前端切换确认框已明确提示）。

## 3. 数据库设计（Supabase / JSON 双库适配）

系统支持两种用户数据库适配器，本次均已兼容：

| 适配器 | 文件 | current_version 处理 |
|--------|------|----------------------|
| Supabase（线上默认） | `backend/database/supabase_db.py` | `public.users` 表新增列；启动时探测列是否存在 |
| 本地 JSON | `backend/database/json_db.py` | 用户记录 JSON 直接新增字段，无 DDL |

### 3.1 Supabase 迁移 SQL（v5.0 必做）

```sql
ALTER TABLE public.users ADD COLUMN IF NOT EXISTS current_version TEXT DEFAULT '';
```

- PostgREST/Supabase 客户端**不能执行 DDL**，该语句只能由管理员在 Supabase 控制台 **SQL Editor** 手动执行（本次已于 2026-09-26 在线上 PRODUCTION 库 `ros2web` 执行成功，`Success. No rows returned`）。
- 新增/更新用户时写入 `current_version`；读取用户记录时透传该字段。

### 3.2 列就绪探测与无重启自愈

为避免"线上库忘了加列导致切换静默失败"，在 Supabase 适配器中加入：

- 实例标志 `current_version_column_ok`：`_migrate_onboarding_columns()` 初始化时用
  `select current_version limit 1` 探测列是否存在（`backend/database/supabase_db.py`）；
- `recheck_version_column()`（`supabase_db.py:81`）：实时复查列状态。管理员补列后**无需重启服务**，下一次切换即成功；
- `update_user()` 捕获 PostgREST `PGRST204`（schema 缓存中无此列），自动把标志置为 `False` 并输出带 SQL 的错误日志。

JSON 适配器无此标志，`_version_column_ready()` 恒为 `True`。

## 4. 后端接口设计

路由文件：`backend/routers/api.py`，版本相关公共辅助函数位于该文件 `_set_user_current_version()`（`api.py:2531` 附近）。

### 4.1 接口清单

| 方法 | 路径 | 说明 | 关键行 |
|------|------|------|--------|
| GET | `/api/install/status` | 安装状态（路径已版本感知） | `api.py:2444` |
| POST | `/api/install/upload` | 上传压缩包 → 版本化解压 → 自动切换新版本 | `api.py:2560` |
| GET | `/api/install/versions` | 版本列表 + 当前版本 + 是否存在旧版 | `api.py:2659` |
| POST | `/api/install/versions/switch` | 切换当前（或目标）用户版本 | `api.py:2681` |
| GET | `/api/install/tree` | 安装目录树（当前版本） | `api.py:2723` |
| POST | `/api/install/delete` | 删除版本；删除当前版本时自动重选并清理 Docker 产物 | `api.py:2812` |

### 4.2 切换接口

`POST /api/install/versions/switch`

请求体：
```json
{ "version": "test_install20260904_x86_ros2_5.0", "target_user": "可选，仅管理员" }
```
- `version` 传**空串** = 回退旧版 install 目录（允许旧版目录尚不存在）。
- 非空版本会校验：版本名合法（`is_valid_version_name`）+ 目录确实存在于该用户空间。
- 普通用户传 `target_user` 返回 403。
- 成功响应：
```json
{ "success": true, "current_version": "...", "message": "已切换到版本 ...，页面即将自动刷新", "need_refresh": true }
```
- 写审计日志，动作类型 `install_version_switch`，并失效 `install_status` 内存缓存。

### 4.3 上传接口（版本化解压 + 自动切换）

`POST /api/install/upload` 流程：

1. 接收 `.zip / .tar.gz / .tgz / .tar.bz2 / .tar`（上限 5GB）；
2. 调 `extract_versioned_install()`（`backend/core/utils.py:387`）完成版本化解压；
3. 校验产物 `<版本目录>/install/setup.bash` 存在；
4. 调 `_set_user_current_version()` 把当前用户 `current_version` 自动置为新版本；
5. 返回 `version`、`host_install`、`auto_switched` 等字段；前端在 `auto_switched=true` 时自动刷新整页。

版本名识别规则（`extract_versioned_install` 内，按优先级）：

1. 压缩包内为 `X/install/...` → 版本名取顶层目录 `X`；
2. 压缩包内为 `X/setup.bash`（X 即 install 内容）→ 版本名取压缩包文件名，并自动包一层 `install/`；
3. 压缩包内顶层即 `install/...` → 版本名取压缩包文件名；
4. 顶层直接是 install 内容（含 setup.bash）→ 版本名取压缩包文件名，自动包一层 `install/`。

版本名经 `sanitize_version_name()` 清洗并排除保留名（`VERSION_RESERVED_NAMES`，如 `Docker`、`install` 等），非法则中止上传并报错。

同名版本已存在时，旧目录备份为 `<版本名>.replaced.<时间戳>`，由 `_prune_backups()`（`backend/core/utils.py:482`）最多保留 2 份。

### 4.4 版本删除接口

`POST /api/install/delete?version=<名>`：

- 删除的目录会改名为 `<名>.deleted.<时间戳>` 备份；
- 若删除的正是当前生效版本：
  1. 调 `_cleanup_user_docker_dir()` 同步清理容器侧 bags/logs/scripts/bk 等生成产物；
  2. 自动把 `current_version` 切到剩余最新版本；没有剩余版本则置空回退旧版；
  3. 自动重选保存失败仅记录告警日志，不阻断删除结果。

### 4.5 版本列表过滤

`list_user_versions()`（`backend/core/workspace.py:58`）扫描工作空间，仅返回"目录内含有 `install/setup.bash`"的合法版本，并通过
`_VERSION_BACKUP_RE = r'\.(deleted|bak|replaced)\.\d{8,}$'`（`workspace.py:32`）
配合 `is_version_backup_entry()`（`workspace.py:35`）过滤全部备份目录。

## 6. 关键业务流程

### 6.1 上传新版本

```
选择压缩包 → 上传(进度条) → 后端解压到临时目录并识别结构
  → 落位 <ws>/<版本名>/install/（同名旧目录先 .replaced 备份，保留2份）
  → 校验 setup.bash → 写用户 current_version
  → 返回 auto_switched=true → Toast 成功 → 1.5s 后整页刷新
  → 所有菜单基于新版本路径
```

### 6.2 切换版本

```
下拉选择 → 二次确认（提示重新生成脚本）
  → POST /versions/switch（校验版本存在 + 权限）
  → 更新 users.current_version → 审计 + 清缓存
  → Toast 成功 → 1.2s 后整页刷新 → 侧边栏/首页徽标更新
```

### 6.3 回退旧版

下拉选择"旧版 install"（空串）→ 同一切换接口 → `current_version=''` →
`resolve_versioned_install()` 回退到 `<ws>/install/`。旧版目录不存在也允许切换（等同未安装状态）。

### 6.4 管理员代操作

管理员在首页用户切换器选择目标用户后：版本列表、上传、切换、删除全部带 `target_user`，
后端以目标用户的 `home_folder_path` + `current_version` 解析路径，并受 `validate_user_path()` 路径遍历保护。

## 7. 本次「切换失败」问题排查记录（PGRST204）

### 7.1 现象

首页选择版本点"切换版本"，红色提示"版本切换保存失败，请重试"；浏览器 Network 中 `/api/install/versions/switch` 返回 `success:false`。

### 7.2 根因

线上使用 Supabase（`SupabaseDatabase`），而 `public.users` 表**尚未创建 v5.0 新增的 `current_version` 列**。
`update_user` 更新该字段时 PostgREST 返回 **`PGRST204`（schema 缓存中不存在该列）**，导致持久化失败。
服务启动日志中其实已有 WARNING，但旧代码把底层错误吞掉，只向前端返回了笼统的"请重试"，用户无法定位。

本地复现实测：
```
adapter: SupabaseDatabase
current_version_column_ok: False
recheck result: False
```

### 7.3 修复内容

1. `backend/database/supabase_db.py`
   - 启动时探测列并维护 `current_version_column_ok`；
   - 新增 `recheck_version_column()` 实时复查；
   - `update_user()` 识别 `PGRST204 / schema cache` 关键字，置位标志并打印修复 SQL。
2. `backend/routers/api.py`
   - 新增 `_VERSION_COLUMN_MISSING_HINT` 与 `_version_column_ready()`（标志为 False 时先实时复查，实现补列后免重启自愈）；
   - `_set_user_current_version()` 改为返回 `(ok, error)`，列缺失时返回带完整 SQL 的中文指引；
   - switch / upload / delete 三处调用全部适配；上传时即使自动切换持久化失败，也保留"文件已解压成功"的事实并以警告提示。
3. `frontend/js/sj_script.js`
   - Toast 长错误延时 + 换行展示；上传部分成功（`auto_switched=false`）时以 warning 展示后端 message。
4. 在 Supabase SQL Editor 执行：
   ```sql
   ALTER TABLE public.users ADD COLUMN IF NOT EXISTS current_version TEXT DEFAULT '';
   ```
   执行成功（`Success. No rows returned`）后实时复查结果变为 `True`，版本切换功能恢复正常，无需重启服务。
