## 1. 代码现状概述

### 1.1 运行逻辑

脚本通过 UDP（`socket.SOCK_DGRAM`）以固定 1 秒间隔，向目标地址循环上报红绿灯状态报文，报文格式为：

```
1@{"method": "rt_message", "params": {"sn": "hz_test_light01", "light_state": 1, "timestamp": 1727400000}}
```

- `1@` 前缀为协议版本标记；
- 载荷为明文 JSON，包含设备序列号 `sn`、灯态 `light_state`、Unix 时间戳 `timestamp`；
- 当前仅启用绿灯阶段（30 秒一轮），红/黄阶段被注释。

### 1.2 关键配置（硬编码）

| 配置项 | 值 | 说明 |
|--------|-----|------|
| `TARGET_IP` | `106.14.223.60` | 阿里云公网 IP，接收方地址 |
| `TARGET_PORT` | `1234` | UDP 接收端口 |
| `DEVICE_SN` | `hz_test_light0X` | 设备序列号，三脚本各不相同 |
| 协议 | 明文 UDP + JSON | 无加密、无认证、无签名 |

## 3. 漏洞详细分析

### F1. UDP 上报协议无认证 —— 设备伪造与灯态欺骗（HIGH）

**风险描述**

报文仅由明文 JSON 构成，`sn` 字段为普通字符串，无任何身份凭证（Token / 密钥 / 签名）。接收方在 UDP 1234 端口被动接收，无法区分报文来自真实设备还是攻击者。攻击者只要：

1. 获知目标 IP 与端口（F2 已暴露）；
2. 构造相同格式的 JSON 字符串（协议格式可从本脚本或抓包直接获得）；

即可向服务端注入任意 `sn`、任意 `light_state` 的伪造报文，造成：
- 红绿灯状态被篡改（如上报绿灯为红灯，干扰调度逻辑）；
- 冒充合法设备注入虚假数据；
- 大量伪造报文挤占接收方处理能力。

**可达性验证**：`build_msg` 输出完全由本地常量与入参决定，无任何鉴权字段；`sock.sendto` 直接发往公网 IP。Source（攻击者主机）→ Sink（服务端 1234 端口）链路完整可达。

**影响**：在红绿灯调度/监控场景下，伪造灯态可能导致错误决策，属直接可利用的高危漏洞。

---

### F2. 生产服务器公网 IP 硬编码于源码（MEDIUM）

**风险描述**

`TARGET_IP = "106.14.223.60"` 为阿里云公网 IP，直接写死在源码中。一旦脚本进入版本库、被打包分发或被外部人员获取，生产资产地址即暴露，攻击者可：
- 对该 IP 进行端口扫描、服务指纹识别；
- 配合 F1 对 UDP 1234 端口发动伪造报文攻击；
- 作为攻击面侦察的入口。

**改进方向**：IP/端口应从配置文件或环境变量读取，源码中不出现生产地址。

---

### F3. 报文无完整性校验 —— 传输可被篡改（MEDIUM）

**风险描述**

UDP 为无连接、无校验的传输层协议，报文 JSON 载荷无 HMAC / 数字签名。链路上的中间人（或能向接收路径注入 UDP 的攻击者）可拦截并修改 `light_state`、`sn`、`timestamp` 字段后转发，接收方无法识别篡改。

与 F1 的区别：F1 是「无身份认证可主动伪造」，F3 是「无完整性保护可被动篡改」。两者叠加使报文的真实性与完整性均无保障。

---

### F4. 明文传输设备 SN 与运行状态（LOW）

**风险描述**

报文未加密，`sn`、`light_state`、`timestamp` 以明文 JSON 在公网传输。网络观察者（ISP、链路设备、抓包者）可直接读取：
- 设备序列号（设备身份信息）；
- 灯态切换规律（绿灯 30s 一轮，可推断运行模式）；
- 时间戳（可用于关联分析）。

虽非高敏感数据，但明文传输违反最小信息暴露原则。

---

### F5. 设备序列号硬编码，可被冒用（LOW）

**风险描述**

`DEVICE_SN` 作为设备唯一标识被硬编码于源码，且（结合 F1）链路无认证。任何获知 SN 的人均可冒用该 SN 上报数据，服务端无法区分报文来源真伪。三脚本使用 `light01/02/04` 等可预测的递增命名，进一步降低猜测成本。

---

### F6. `sendto` 无异常处理，网络错误导致脚本崩溃（LOW）

**风险描述**

```python
def send_light_phase(light_state, duration, interval=1):
    start_time = time.time()
    while time.time() - start_time < duration:
        data = build_msg(light_state)
        sock.sendto(data, (TARGET_IP, TARGET_PORT))   # 无 try/except
        time.sleep(interval)
```

`sock.sendto` 在网络中断、路由变更、目标不可达时可抛出 `OSError`/`socket.error`。当前仅外层 `try/except KeyboardInterrupt` 捕获键盘中断，网络异常会直接终止脚本，灯态上报静默中断，运行方无感知。

---

### F7. 模块级 Socket 创建，导入即泄漏文件描述符（LOW）

**风险描述**

```python
sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)   # 模块级，import 即执行
```

`sock` 在模块加载时即创建，但 `sock.close()` 仅在 `if __name__ == "__main__"` 的 `finally` 中调用。若脚本被作为模块 `import`（例如未来集成进更大系统），socket 文件描述符将一直泄漏直至解释器退出。

---

### F8. `light_state` 未校验合法枚举值（LOW）

**风险描述**

`build_msg(light_state: int)` 的类型注解为 `int`，但运行时不校验 `light_state` 是否为已定义的 `LIGHT_GREEN/LIGHT_RED/STATE_OFF/LIGHT_YELLOW` 之一。调用方传入任意整数（如 `0`、`99`）会被直接拼入 JSON 上报，服务端可能收到未定义灯态并产生解析/逻辑异常。

此外代码存在状态定义与使用不一致：`STATE_OFF = 3` 已定义但从未使用；`YELLOW_DURATION = 3` 定义为 3 秒，但被注释的调用处硬编码为 `5` 秒，存在配置漂移风险。

## 4. 改进方案

### 4.1 即时改进（低成本、高收益，应立即实施）

| 编号 | 改进项 | 对应漏洞 | 实施要点 |
|------|--------|---------|---------|
| I-1 | 配置外部化 | F2、F5 | 将 `TARGET_IP`/`TARGET_PORT`/`DEVICE_SN`/灯态时长移至独立配置文件（如 `config.json` 或 `.env`），源码不出现生产地址；配置文件加入 `.gitignore` |
| I-2 | `sendto` 异常捕获与重连 | F6 | 在 `send_light_phase` 内对 `sendto` 包裹 `try/except OSError`，失败时记录日志并指数退避重试，避免单次网络抖动导致整体退出 |
| I-3 | `light_state` 枚举校验 | F8 | `build_msg` 入口校验 `light_state in {LIGHT_GREEN, LIGHT_RED, STATE_OFF, LIGHT_YELLOW}`，非法值直接 `raise ValueError` |
| I-4 | Socket 生命周期治理 | F7 | 将 `sock` 创建移入 `main()` 函数内，使用 `with` 上下文或 `try/finally` 确保释放；模块级仅保留常量定义 |
| I-5 | 清理状态定义不一致 | F8 | 统一 `YELLOW_DURATION` 与调用处一致，移除未使用的 `STATE_OFF` 或为其补充调用 |

### 4.2 协议安全加固（中成本，核心风险根治）

| 编号 | 改进项 | 对应漏洞 | 实施要点 |
|------|--------|---------|---------|
| P-1 | 引入 HMAC 报文签名 | F1、F3 | 每台设备预置唯一密钥 `DEVICE_SECRET`；报文增加 `sign` 字段 = `HMAC-SHA256(DEVICE_SECRET, payload)`；服务端按 `sn` 查密钥验签，验签失败丢弃。密钥不入源码，随配置下发 |
| P-2 | 引入设备 Token / 时间窗口 | F1 | 报文增加 `nonce` + 短时效 `token`（如 JWT），服务端校验时效与来源，防止重放与伪造 |
| P-3 | 报文加密传输 | F4 | 若上报通道需经公网，改用 DTLS（UDP over TLS）或将上报改走 HTTPS/WSS（与平台 8875 端口复用鉴权体系），载荷加密传输 |
| P-4 | 接收端速率限制与黑白名单 | F1 | 服务端按 `sn` 做速率限制，异常 `sn`/异常频次告警，降低伪造报文的实际影响 |

### 4.3 架构演进（长期，与平台统一）

| 编号 | 改进项 | 对应漏洞 | 实施要点 |
|------|--------|---------|---------|
| A-1 | 上报通道并入平台鉴权体系 | F1、F4、F5 | 红绿灯上报不再裸 UDP 直连，改为走平台 WebSocket / REST API（复用 Mock Truck Web 的 JWT 鉴权），设备以登录态上报，天然具备身份认证与加密 |
| A-2 | 设备身份注册与密钥管理 | F1、F5 | 建立设备注册表（可复用 Supabase `users` 表模式），设备首次入网注册获取 `sn`+`secret`，密钥可轮换、可吊销 |
| A-3 | 上报日志与审计 | — | 上报行为落审计日志（复用平台 `add_audit_log`），异常灯态/异常来源可追溯 |
| A-4 | 配置热加载 | F2 | 灯态时长、上报间隔等支持运行时热加载，避免改配置需重启脚本 |

## 5. 开发方案（分阶段路线图）

### 阶段一：即时加固（v0.1-security-patch）

**目标**：消除信息泄漏与崩溃风险，零架构改动，可当天上线。

**任务清单**

1. **配置外部化**：新建 `config.json`（或 `.env`），迁移 `TARGET_IP`/`TARGET_PORT`/`DEVICE_SN`/三色时长；脚本启动时读取，缺失时以安全默认值（如 `127.0.0.1`）启动并告警；配置文件纳入 `.gitignore`。
2. **网络异常治理**：`send_light_phase` 内 `try/except OSError`，失败日志 + 指数退避（1s→2s→4s，上限 30s），连续失败 N 次打印告警但不退出。
3. **灯态枚举校验**：`build_msg` 入口校验合法灯态，非法值 `raise ValueError`。
4. **Socket 生命周期**：`sock` 创建移入 `main()`，`with closing(socket(...)) as sock` 确保释放。
5. **状态定义清理**：统一 `YELLOW_DURATION`，补齐或移除 `STATE_OFF`。

**验收标准**

- 源码 `grep` 不再出现 `106.14.223.60`；
- 断网/拔网线场景脚本不崩溃，恢复网络后自动续传；
- 传入非法 `light_state` 时脚本报错退出而非发送脏数据；
- `import` 模块不产生泄漏的 socket fd。

---

### 阶段二：协议安全加固（v0.2-secure-protocol）

**目标**：根治伪造与篡改，使上报报文具备身份认证与完整性。

**任务清单**

1. **HMAC 签名方案**：
   - 设备配置新增 `DEVICE_SECRET`（每台唯一，16+ 字节随机）；
   - 报文结构升级为 `1@{...payload..., "sign": "hmac-sha256-hex"}`，`sign = hmac.new(secret, payload_json, sha256).hexdigest()`；
   - 报文增加 `nonce`（随机）+ 已有 `timestamp`，服务端做时间窗口（如 ±60s）+ nonce 去重防重放；
   - 协议版本号 `1@` 升至 `2@`，服务端兼容旧版过渡期。
2. **接收端验签改造**（需服务端配合）：按 `sn` 查 `DEVICE_SECRET`，验签失败丢弃并审计告警。
3. **密钥下发机制**：密钥随配置文件下发，不入源码；密钥轮换接口预留。

**验收标准**

- 攻击者无密钥时，伪造报文被服务端 100% 拒绝；
- 截获并篡改任意字段的报文验签失败；
- 重放 60 秒前的报文被拒绝；
- 新旧协议可并行过渡，不影响存量设备。

---

### 阶段三：并入平台统一鉴权（v1.0-platform-integrated）

**目标**：上报通道与 Mock Truck Web 平台鉴权体系统一，消除独立裸 UDP 通道的根本风险。

**任务清单**

1. **通道迁移**：红绿灯上报改走平台 WebSocket（已有 `ws_clients` 体系）或 REST API，复用 JWT Bearer 鉴权；设备以独立账号登录获取 token。
2. **加密传输**：平台已支持 HTTPS/WSS（`HTTPSRedirectMiddleware`），上报天然加密。
3. **设备注册表**：复用 Supabase `users` 表或新建 `devices` 表，管理 `sn`/`secret`/`token`/启停状态/最后上报时间。
4. **审计与告警**：上报异常（验签失败、灯态跳变、断连）写入平台审计日志与告警中心（对接 v5.2 异常告警能力）。
5. **配置热加载**：灯态时长、上报间隔支持通过平台下发，免重启调整。

**验收标准**

- 上报通道不再有裸 UDP 公网端口；
- 设备需持有效 JWT 上报，无凭证请求被 401 拒绝；
- 上报行为可在平台审计日志中追溯；
- 灯态配置可通过平台热更新。

## 7. 结论

当前三份红绿灯上报脚本存在一项**高危**（无认证可伪造灯态）、两项**中危**（生产 IP 硬编码、无完整性校验）及多项**低危**问题。其中 F1（无认证伪造）与 F2（IP 暴露）组合后形成完整可利用攻击链：攻击者可从源码获取目标地址，直接构造伪造报文篡改灯态，对红绿灯调度场景构成直接威胁。

**建议处置路径**：

1. **立即**（阶段一）：完成配置外部化与异常处理，消除 IP 泄漏与崩溃风险——零架构改动即可上线；
