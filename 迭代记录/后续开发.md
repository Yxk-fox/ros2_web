## 1. 编制说明

### 1.1 编制背景

v5.0 已完成 install 目录多版本管理与切换功能的全量交付（上传版本化归档、首页切换、全局路径生效、Supabase/JSON 双库适配、PGRST204 缺列自愈），系统当前处于稳定运行状态。本计划基于当前代码基线，规划后续三个版本的开发方向。

### 1.2 优先级口径

经评审确认的四个优先方向（按优先级降序）：

| 序 | 方向 | 归属里程碑 |
|----|------|-----------|
| 1 | 版本管理深化 | v5.1 |
| 2 | 测试与质量保障 | v5.2 |
| 3 | 运维监控增强 | v5.2 |
| 4 | 架构演进 | v6.0 |

### 1.3 计划结构

采用「里程碑主线 + 任务矩阵」双维度组织：

- **主线**：v5.1（短期收尾）→ v5.2（中期加固）→ v6.0（远期演进）；
- **矩阵**：每个里程碑内按模块列出 P0–P2 任务，每项任务包含目标、实现要点、涉及文件、验收标准与风险。

## 2. 现状基线（v5.0 已交付能力）

后续开发建立在以下已交付能力之上，新的改动**不得破坏**这些行为的兼容性：

| 领域 | 已交付能力 | 关键实现 |
|------|-----------|---------|
| install 版本管理 | 上传压缩包按顶层目录名归档为 `<工作空间>/<版本>/install/`；首页下拉切换/删除；同名重传自动备份（保留 2 份）；删除当前版本自动重选 | `core/workspace.py`（`resolve_versioned_install` / `list_user_versions`）、`core/utils.py`（`extract_versioned_install` / `_prune_backups`）、`routers/api.py`（`/api/install/*`） |
| 全局路径生效 | 版本切换后所有菜单（脚本/仿真/话题/节点/服务/Action/工单等）统一在所选版本目录下工作；宿主机 ROS2 命令 source 当前版本 `setup.bash` | `get_user_workspace_paths()` 单一入口 + `get_admin_install_dir()` |
| 数据库适配 | Supabase/JSON 双库均支持 `current_version` 字段；Supabase 缺列探测 + PGRST204 捕获 + 免重启自愈 | `database/supabase_db.py`（`recheck_version_column`）、`database/json_db.py` |
| 容器与数据导出 | 容器全生命周期管理；hdmap 提取、ros2 bag 录制（mcap）与 Web 下载 | `services/docker_manager.py`、`services/data_export_service.py` |
| 前端体验 | 侧边栏版本徽标、首页版本区块、上传分片进度、Toast 长消息自适应 | `frontend/js/sj_script.js`（17b 章节） |

**已知遗留问题**（v5.0 文档明确记录，作为 v5.1 输入）：

1. 切换版本前已生成的启动脚本内路径是**固化的**，切换后需手动重新生成脚本（前端仅有确认框提示）；
2. 容器内运行版本依赖**手动重启仿真容器**完成新版本挂载；
3. 磁盘上的备份目录（`.deleted/.bak/.replaced.<时间戳>`）不显示在版本列表，**无前端清理入口**，需管理员登录服务器手动清理；
4. `bag_storage` 目录为用户级（`home/Docker/bags`），与 install 版本无关，跨版本测试的 bag 数据混存；
5. Supabase 库重建/迁移后需重新执行 DDL（已有日志提示与自愈，但依赖人工关注日志）。

## 4. v5.1 里程碑：版本管理深化

### 4.1 里程碑目标

将 v5.0 的「手动切换 + 手动重新生成脚本 + 手动重启容器」三级操作链路，收敛为「一键切换、自动生效」，并补齐版本元数据与备份管理能力。**原则：不改变 v5.0 的目录结构与数据库字段语义，只做增量。**

### 4.2 任务矩阵

#### T-5.1-01【P0】切换版本后自动重新生成启动脚本

| 项 | 内容 |
|----|------|
| 目标 | 版本切换持久化成功后，自动扫描新版本 `launch_dir` 并重新生成启动脚本，消除「脚本路径固化」遗留问题 |
| 实现要点 | 1. `/api/install/versions/switch` 成功路径中追加可选参数 `regenerate_scripts=true`（默认 true，可关闭）；2. 复用 `ROS2ScriptGenerator` 现有生成流程，基于切换后的 `launch_dir` 执行；3. 生成前将旧脚本目录整体备份为 `scripts.bak.<时间戳>`（复用 `_prune_backups`，保留 2 份）；4. 生成结果（成功数/失败数）随 switch 响应返回，前端 Toast 展示 |
| 涉及文件 | `backend/routers/api.py`、`backend/services/script_generator.py`、`frontend/js/sj_script.js`（`switchInstallVersion`） |
| 验收标准 | ① 切换后 30 秒内脚本完成重生成且指向新版本路径；② 生成失败不阻断切换结果（降级为 warning 提示）；③ 关闭 `regenerate_scripts` 时行为与 v5.0 完全一致 |
| 风险 | 旧脚本被用户手工编辑过的内容会丢失 → 生成前自动备份可回滚；响应时间变长 → 生成流程放后台线程，switch 立即返回，结果经 WebSocket `broadcast_log` 推送 |

#### T-5.1-02【P0】切换版本后自动重启仿真容器挂载新版本

| 项 | 内容 |
|----|------|
| 目标 | 切换版本后自动重启该用户（或管理员 target_user）名下的 ROS2 仿真容器，使新版本 install 挂载到容器内固定路径 `/home/boonray/install`，消除手动重启环节 |
| 实现要点 | 1. switch 接口追加 `restart_containers=true`（默认 false，前端确认框中由用户勾选，确认文案同步调整）；2. 通过 `db.get_visible_container_names(user)` 定位目标用户容器，逐一 `docker restart`；3. 重启为异步批量操作，进度经 WebSocket 推送；4. 容器重启失败逐台记录，不中断其余容器 |
| 涉及文件 | `backend/routers/api.py`、`backend/services/docker_manager.py`、`frontend/js/sj_script.js`（确认框 + 结果展示） |
| 验收标准 | ① 勾选后容器内 `/home/boonray/install/setup.bash` 与所选版本一致；② 录制中的 bag 会话存在时**拒绝自动重启**并提示先停止录制（防数据损坏）；③ 不勾选时行为与 v5.0 一致 |
| 风险 | 误停正在执行长任务的容器 → 默认值 false + 二次确认 + bag 录制检测三重防护；容器数量多时重启耗时长 → 异步化 + 超时保护（单台 60s） |

#### T-5.1-03【P1】版本元数据（备注 / 大小 / 上传时间）

| 项 | 内容 |
|----|------|
| 目标 | 版本列表展示大小、上传时间、备注，支撑版本选型决策 |
| 实现要点 | 1. 元数据不新建表：大小/时间由 `list_user_versions()` 扫描目录时用 `os.stat` 采集（`st_mtime` + `du` 等效计算，考虑目录较大时异步缓存）；2. 备注存入用户记录的扩展字段 `version_notes`（JSON 对象：`{版本名: 备注文本}`，Supabase 需同步 DDL：`ADD COLUMN IF NOT EXISTS version_notes JSONB DEFAULT '{}'`，复用缺列探测自愈机制）；3. 新增 `PUT /api/install/versions/{version}/note` 端点；4. 前端版本列表增加备注列与行内编辑 |
| 涉及文件 | `backend/core/workspace.py`、`backend/routers/api.py`、`backend/database/supabase_db.py`、`backend/database/json_db.py`、`frontend/js/sj_script.js` |
| 验收标准 | ① 版本列表显示三项元数据；② 备注可编辑并持久化（双库一致）；③ 目录大小计算不阻塞版本列表加载（>2GB 目录走后台缓存，先显示"—"） |
| 风险 | 大目录扫描拖慢接口 → 首次异步计算 + `SimpleCache` 缓存 5 分钟；Supabase 忘加列 → 复用 `current_version` 的探测/自愈模式 |

#### T-5.1-04【P1】一键回滚上一版本

| 项 | 内容 |
|----|------|
| 目标 | 新版本验证失败时，一键回滚到切换前的版本（含脚本与容器联动） |
| 实现要点 | 1. 用户记录新增 `previous_version` 字段（switch 时自动记录旧值，含时间戳）；2. 首页版本区块增加「↩ 回滚上一版」按钮，仅在 `previous_version` 对应目录仍存在时可用；3. 回滚 = 带确认的 switch 到 `previous_version`（自动携带 T-5.1-01/02 的联动）；4. 回滚本身也更新 `previous_version`，形成可往返的历史链（最多记忆 1 步，避免无限链） |
| 涉及文件 | `backend/routers/api.py`、`backend/core/workspace.py`、`backend/database/supabase_db.py`、`backend/database/json_db.py`、`frontend/js/sj_script.js` |
| 验收标准 | ① 回滚后 `current_version`、脚本、容器挂载全部一致回到旧版本；② 回滚操作写审计日志（action=`install_version_rollback`）；③ `previous_version` 目录已被删除时按钮置灰并提示 |
| 风险 | 与手工 switch 混用导致历史链错乱 → `previous_version` 只在成功 switch 时覆写，语义单一 |

#### T-5.1-05【P2】备份目录前端可视化管理

| 项 | 内容 |
|----|------|
| 目标 | `.deleted/.bak/.replaced.<时间戳>` 备份目录提供前端查看/恢复/清理入口，替代登录服务器手动管理 |
| 实现要点 | 1. 新增 `GET /api/install/backups`：列出工作空间内全部备份目录（名、类型、时间戳、大小）；2. `POST /api/install/backups/restore`：将某备份目录恢复为正式版本（同名冲突时现行版本自动转为 `.bak` 备份）；3. `DELETE /api/install/backups?entry=<名>`：物理删除指定备份；4. 前端版本区块增加「备份管理」折叠区，操作均带二次确认 |
| 涉及文件 | `backend/core/workspace.py`（复用 `is_version_backup_entry`）、`backend/routers/api.py`、`frontend/js/sj_script.js` |
| 验收标准 | ① 备份列表与磁盘实际一致且**不混入**正式版本列表；② 恢复后版本可正常切换使用；③ 物理删除有审计日志 |
| 风险 | 物理删除不可逆 → 红色按钮 + 输入目录名确认（与删除容器同级别防护） |

### 4.3 里程碑验收清单

- [ ] 切换版本勾选联动后：脚本自动重生成、容器自动重启挂载，全程无手工干预
- [ ] bag 录制中时自动重启被拒绝并明确提示
- [ ] 版本列表展示大小/时间/备注，备注可编辑
- [ ] 一键回滚可用，且回滚同样享受联动
- [ ] 备份目录可在前端查看/恢复/清理
- [ ] 未启用新参数时，全部行为与 v5.0 完全一致（零破坏回归）
- [ ] Supabase 模式 DDL 变更有缺列探测与免重启自愈

## 5. v5.2 里程碑：质量保障与运维监控

### 5.1 里程碑目标

为 v5.x 系列建立的版本管理、容器联动等关键链路补齐自动化测试底座；同时将监控从「实时快照」升级为「历史趋势 + 主动告警」，使问题可度量、可回溯。

### 5.2 任务矩阵

#### T-5.2-01【P0】后端单元测试底座（pytest）

| 项 | 内容 |
|----|------|
| 目标 | 建立单元测试框架并优先覆盖版本管理核心纯函数，防回归 |
| 实现要点 | 1. 新增 `backend/tests/` 目录与 `pytest` + `pytest-cov` 依赖（写入 requirements）；2. 首批覆盖：`workspace.py` 的 `resolve_versioned_install` / `list_user_versions` / `is_valid_version_name` / `is_version_backup_entry`、`utils.py` 的 `extract_versioned_install`（临时目录构造各类压缩包结构：`X/install`、顶层即 install、顶层为 install 内容、非法版本名、同名替换备份）；3. 数据库适配器用接口契约测试（同一用例集分别跑 `JsonDatabase` 与 mock 的 Supabase 适配器）；4. CI 前先以本地 `make test` / `python -m pytest` 形式交付 |
| 涉及文件 | 新增 `backend/tests/test_workspace.py`、`backend/tests/test_utils_extract.py`、`backend/tests/test_db_contract.py`；`redame/requirements.txt` 追加依赖 |
| 验收标准 | ① 版本管理核心函数行覆盖率 ≥ 85%；② P0 两条链路（上传解压、切换解析）有端到端级函数测试；③ 全量测试 60 秒内跑完 |
| 风险 | 测试依赖真实 Docker → 单元测试仅覆盖纯逻辑，Docker 相关留到 v6.0 E2E；`run_ros2_cmd` 等宿主机命令通过 monkeypatch 打桩 |

#### T-5.2-02【P1】deploy.py 部署前自动回归检查

| 项 | 内容 |
|----|------|
| 目标 | 部署前自动跑单测 + 健康检查，阻止带病上线 |
| 实现要点 | 1. `deploy.py` 增加 `--run-tests` 参数（默认开启，`--skip-tests` 跳过）：部署前执行 `python -m pytest backend/tests -q`，失败即中止；2. 部署完成后自动 curl `/` 与 `/api/system/status`（无鉴权路径）做健康探测；3. 失败时输出明确回滚指引（systemd 保留的旧代码目录 + `systemctl restart`） |
| 涉及文件 | `deploy.py` |
| 验收标准 | ① 单测失败时部署中止且退出码非 0；② 部署后健康检查失败时日志给出回滚步骤；③ `--skip-tests` 显式跳过时在日志中留痕 |
| 风险 | 服务器无 pytest 环境 → deploy 已有依赖安装流程，追加安装即可 |

#### T-5.2-03【P1】资源监控历史曲线

| 项 | 内容 |
|----|------|
| 目标 | CPU/内存/GPU/容器资源从实时快照升级为可回看的历史曲线 |
| 实现要点 | 1. 新增 `services/metrics_history.py`：后台线程每 30s 采样一次（复用 `SystemMonitor.get_system_status` 与 `docker stats --no-stream` 聚合），写入本地 SQLite（`data/metrics.db`，单表 + 滚动清理保留 7 天）；2. 新增 `GET /api/system/metrics/history?metric=&range=` 查询接口；3. 前端监控面板增加「趋势」视图，用轻量 SVG 折线（不引入图表库，保持零构建）；4. 采样失败静默跳过，不影响主服务 |
| 涉及文件 | 新增 `backend/services/metrics_history.py`、`backend/routers/api.py`、`frontend/js/sj_script.js`、`frontend/index.html`（趋势视图容器） |
| 验收标准 | ① 可查看近 1h/6h/24h/7d 四档曲线；② 采样线程崩溃自动重启且不拖垮主进程；③ SQLite 文件超 100MB 自动裁剪 |
| 风险 | 采样增加系统负载 → 30s 间隔 + 聚合采样实测 CPU 开销 < 1%；SQLite 写入锁 → WAL 模式 + 独立连接 |

#### T-5.2-04【P2】仿真运行报告

| 项 | 内容 |
|----|------|
| 目标 | 自动统计脚本批量执行的启动成功率、耗时分布，形成可导出的运行报告 |

## 7. 横切关注点

以下约定贯穿三个里程碑，任一任务的实现均须遵守：

### 7.1 兼容性红线

1. **目录结构不变**：`<工作空间>/<版本>/install/` 结构、`current_version` 字段语义、旧版 `<ws>/install/` 回退机制不改动；
2. **API 只增不改**：已有端点的路径、请求/响应字段只做向后兼容追加（新增字段/可选参数），破坏性变更须升主版本号（v7.0）；
3. **双库对齐**：任何用户记录新字段必须同时适配 `json_db.py` 与 `supabase_db.py`，Supabase 新列一律 `ADD COLUMN IF NOT EXISTS ... DEFAULT`，并配套缺列探测 + PGRST204 自愈（模式复用 `current_version` 的实现）。

### 7.2 安全基线

1. 新端点一律挂 `Depends(require_permission(...))` 或 `require_admin`，涉及路径的必须过 `validate_user_path()`；
2. 版本名/备注等用户输入统一走 `sanitize_version_name` 级别的清洗，防路径穿越；
3. 破坏性操作（物理删除备份、自动重启容器）一律审计日志 + 二次确认。

### 7.3 性能约定

1. 新增同步阻塞操作（目录扫描、docker 命令）遵循 v3.5 优化经验：高频只读端点用 `def` 走线程池；
2. 大目录操作（大小统计、备份恢复）一律异步 + WebSocket 进度推送，不阻塞 HTTP 响应；
3. 前端不引入构建工具与重量级图表库，趋势图用原生 SVG 实现。

### 7.4 文档同步机制

每个里程碑合入后，同步更新：

| 文档 | 更新内容 |
|------|---------|
| `ck/` 下对应功能开发文档 | 新增该里程碑的功能开发文档（模式对齐《安装目录管理结构迭代.md》） |
| `docs/operations.html` | 新按钮的操作说明 |
| `docs/development.html` | 架构/API/数据库变更 |
| `docs/onboarding.html` | 功能地图与新工作流 |
| `docs/value-report.html` | 里程碑达成情况与价值数据 |
| `ck/后续开发.md` | 勾选验收清单，滚动修订下一里程碑任务 |

### 7.5 发布流程

沿用既有流程：`deploy.py` 部署 → systemd `Restart=always` 换新 → 端口 8875 健康检查。v5.2 起部署前自动回归（T-5.2-02），v6.0 起由 CI 接管。
